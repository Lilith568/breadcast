# Breadcast

**Bake what sells. Waste less.** Breadcast turns a bakery's own sales history into tomorrow's bake quantities per product. It cuts unsold bread without emptying the shelves. Everything runs in the browser, and no data leaves the device.

Built for **Arbiter Hacks V1**, Theme Track **Rethinking Waste**.

- **Live app:** https://lilith568.github.io/breadcast/
- **Demo video:** see the Devpost submission

## The waste problem and how we measure success

Small bakeries decide every evening how much to bake the next morning, usually by rule of thumb ("last weeks' sales plus a safety margin"). Whatever is not sold by closing time is wasted, sold off cheaply or donated. Fresh bread cannot be stored, so over-production is food, energy and money thrown away.

Breadcast is measured by two weekly numbers:
- **Waste rate** = unsold items ÷ baked items.
- **Sold-out rate** = share of days a product ran out before closing.

**Success** means a lower waste rate over four weeks with no higher sold-out rate and no lower margin than the four weeks before. The built-in backtest applies exactly this measurement to past data.

On the synthetic sample bakery (8-week backtest, conservative evaluation), Breadcast cuts unsold items by about **40%** (waste rate 17% → 11%), with about 1% fewer units sold and a slightly higher margin. Counting an extra cost per wasted item (slider) lowers waste further. These numbers come from synthetic data; real bakeries will differ.

## How it works

1. **Data:** CSV with `date, product, baked, sold` and optional `rain, temp_c, holiday`.
2. **Model (machine learning in the browser):** per product, a linear **quantile regression** on `log(1 + sales)` with weekday, seasonality (sine/cosine of day of year), holiday and day-before-holiday flags, rain, temperature, and lagged sales (average of the last four same weekdays and of the last 7 days). It is trained with Adam on the pinball loss, with L2 regularisation and standardised features.
3. **Censored demand:** on sold-out days true demand was *higher* than sales. Those observations only penalise under-prediction, so the model does not learn that a sell-out means low demand. A test checks that this recovers true demand where a naive model underestimates it.
4. **Decision (newsvendor):** the forecast quantile equals the critical ratio `(price − cost) / (price − value_if_unsold + waste_penalty)`. Expensive waste → lower quantile → smaller batch.
5. **Backtest:** train on everything before the last 8 weeks, then compare recommendations with what was actually baked. On sold-out days demand is assumed to equal sales, which can only understate Breadcast's benefit.
6. **Bake plan:** next-day quantity per product with a 25–90% demand range and the main drivers of that day's forecast. Export to CSV or print.

## Run locally

```bash
python3 -m http.server 8000   # open http://localhost:8000
npm test                      # 8 tests, Node 20+
npm run sample                # regenerate the synthetic sample
```

No build step, no dependencies.

## Synthetic sample

`sample-bakery.csv` is generated by `syntheticHistory()` in `forecast.mjs` (seeded, reproducible): 14 months, 5 products, weekday, seasonal, holiday and weather effects with log-normal noise. Its `baked` column follows a rule of thumb: the average of the last four same weekdays plus 20%. It is not real bakery data.

## Limitations

- Linear model: strong, explainable baseline. Gradient boosting or pooled models across products could capture more.
- Weather and holidays for the plan date must be entered by hand. No external API is called.
- The backtest uses one train/test split per product; rolling-origin evaluation would be more robust.
